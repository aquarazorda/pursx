# pursx

JSX syntax for PureScript. A `.purx` file is PureScript in which an expression can also be a JSX element; `pursx` turns it into a `.purs` file of ordinary function calls, which the compiler and every other tool then treat as plain PureScript.

pursx knows no UI library. What JSX turns into (which functions are called, how children are passed) is set in `pursx.json`, so the same syntax works with purs-solid, react-basic or anything else built from functions.

```purescript
counter :: Component {}
counter = Component.component \_ -> do
  count /\ setCount <- createSignal 0
  pure
    <div class="counter">
      <button onClick={\_ -> modify_ setCount (_ + 1)}>+</button>
      <span>{show <$> count}</span>
    </div>
```

With `{ "elements": "H", "singleChild": "bare" }`, the view becomes:

```purescript
  pure
    (H.div { class:"counter" }
      [ (H.button { onClick:(\_ -> modify_ setCount (_ + 1)) } "+")
    , (H.span {} (show <$> count)) ]
         )
```

The generated file has the same lines as the `.purx`, so compiler errors point at the right line.

## Usage

```bash
npm install --save-dev pursx
```

```bash
npx pursx src
```

This writes a `.purs` file next to each `.purx` file under `src`. Run it before `spago build`, or keep it running with `--watch`.

- `pursx [path...]`: convert every `.purx` file under the paths (default `.`). Unchanged files are not rewritten.
- `--watch`: keep converting as files change. Deleting a `.purx` file deletes its `.purs`.
- `--check`: write nothing and fail if any `.purs` is missing or out of date (for CI).
- `--stdout FILE.purx`: print the output instead of writing it.
- `--config FILE`: use these settings instead of the nearest `pursx.json`.

A generated file ends with a `-- Generated by pursx` comment. pursx refuses to overwrite a `.purs` file without it.

Whether to commit the generated files is up to you. A package published to the PureScript registry must include them, because the registry only sees `.purs` files.

## Settings

`pursx.json` is looked up from each file's directory upwards. Every key is optional.

| Key | Default | Meaning |
| --- | --- | --- |
| `elements` | `""` | Qualifier for lowercase tags: with `"H"`, `<div>` calls `H.div`. |
| `children` | `"argument"` | `"argument"`: `div props children`. `"prop"`: `div { ..., children: [...] }`. |
| `singleChild` | `"array"` | With `"argument"`: `"bare"` passes a lone child as is (`span {} "Hi"`, `span {} (x)`); `"array"` always passes an array. |
| `text` | `"text"` | Function wrapping text that is one of several children. |
| `component` | `""` | Function applied to components: with `"Component.element"`, `<Counter n={1} />` is `Component.element counter { n: 1 }`. |
| `voidElements` | HTML's | Lowercase tags called with props only, such as `input` and `br`. |

For purs-solid:

```json
{
  "elements": "H",
  "singleChild": "bare",
  "text": "JSX.text",
  "component": "Component.element"
}
```

For react-basic, where elements take one record with `children`:

```json
{
  "elements": "R",
  "children": "prop",
  "text": "R.text"
}
```

The modules named in these settings must be imported by the file, for example `import Solid.DOM.HTML as H`.

## Syntax

- `<div>`: a lowercase tag calls the element function, qualified by `elements`.
- `<Icons.star />`: a qualified lowercase tag calls that function as written.
- `<Counter />`, `<Todo.Item />`: a capitalized tag is a component, called as `counter` or `Todo.item` through `component`. Its children become a `children` prop.
- `name="text"` passes the string literal, `name={expr}` passes any expression, and `name` alone passes `true`. Names that aren't identifiers, such as `aria-label` or `on:click`, become quoted labels.
- Text follows JSX's whitespace rules, and `&amp;`, `&lt;`, `&gt;`, `&quot;`, `&apos;`, `&nbsp;` and numeric references are decoded. Write `{"<"}` or `{"}"}` for those characters.
- `{- comment -}` is a comment, between children or attributes.
- `{expr}` can hold any expression, including more JSX, `do` blocks and `case`.

JSX is recognised where an expression can start: after `=`, `$`, `->`, an opening bracket, a comma, any other operator, or `then`, `else`, `in`, `of`, `do`, `let`, `where`; or first on a line. That leaves the `<` operator alone, but it has two consequences:

- JSX as an argument needs `$` or parentheses: `f $ <a />` or `f (<a />)`, not `f <a />`.
- An operator section needs a space: `(< b)`, not `(<b)`.

Not supported yet: fragments (`<></>` is PureScript's `<>` operator; use an array), and spread attributes (`{...props}`).

## JavaScript API

For build tools, such as a Vite plugin that converts `.purx` files itself:

```js
import { transform } from "pursx";

const code = transform(source, { elements: "H", singleChild: "bare" });
```

The options are those of `pursx.json`. Bad JSX throws a `SyntaxError` with `line` and `column`; bad options throw a `TypeError`.

The converter is also a PureScript library: `PursX.transform :: Config -> String -> Either Error String`.

## Development

```bash
npm test
```

This runs the PureScript tests, bundles the CLI, and runs its end-to-end tests. The fixtures in `test/fixtures` are `.purx` files with their generated `.purs`. `spago test` compiles the generated files against the stub libraries in `test/Stub`, so the output is type-checked, not only compared. After changing the output, regenerate them with `npm run fixtures` and review the diff.
